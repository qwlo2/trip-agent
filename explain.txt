1.3上下文窗口，compress
   
   当history超过comoress要进行压缩，因此要将摘要也追加到history，考虑重启后如何恢复上下文。
   
   history的变化
   由于要将记录量化做到区分不同记录，增加seq和turn，每一次完整的对话称为turn
   1、可以将摘要单独保存，每次都读取文件然后，然后就可以获取摘要之后哪些seq并没有comress，再进行随机读取
   2、则是将compress也作为history记录，然后顺序读取整个history，每到comress就替换相应的seq
   但是1存储多个不同文件持久化一致的问题，维护困难，暂时采用2

compact：

   comress在history中同样采用追加，但在message中采用replace，将压缩的seq进行替换，
   compress时为了保证tool call和tool resultt联系应该要一起compress

采用正向扫描构建缓存+反向定位
正向：
构建缓存：interface BalanceCache {
    generation: number;缓存是否有效

    cutBalanced: readonly boolean[];n个surface有n+1个node

    indexBySeq: Map<SessionSeq, number>;反向定位通过seq获取在surface的位置从而判断是否安全

    inProgressToolCalls: number;tool-result不一定全部返回，此时将pendig记住配合eventDelta()增量更新位置
}

反向：
通过不断估计token，达到限制k之后，通过seq得到node的位置，再由cutBalanced判断是否安全
这里构建2个函数，判断node前后是否安全，也就是分别查看【node】和【node+1】就可以是实现前后的概念

摘要：
压缩后的摘要也追加到history，参与seq计算，并且要附带说明这是哪些seq压缩而成；
在message中采用replace，将摘要和被压缩的seq替换，保证信息顺序不变；重启时，
message通过读取文件组织seq而来，当遇到压缩的seq，也效仿之前的进行替换，也就是顺序读取，
并不断替换，最终得到完整的mwssage；最后在tool中注册压缩工具，当用户要求压缩时，
llm通过tool-call进行

token估算：
采用UTF8，4字节估算，
T=min（WR，W-o-b）取下
k=（w-o）r取下
W：当前模型的 Context Window。
r：压缩触发比例，沿用 DSH 的策略。
O：输出预留，设置为当前模型支持的最大输出 Token。
B：安全预留，同样设置为当前模型支持的最大输出 Token。



1.4、记忆模块

    设定为局部记忆和全局记忆，局部即是session的提炼，开始、过程和结果，全局记忆是用户画像，即
用户偏好，项目经历，以及各种约束

存储结构：
    event-log
    局部记忆-sqlite(通过数据库管理元数据，记录使用次数等，也方便提权来压缩全局)
    （增加变量标记是否参与全局提取）
    全局记忆-md

phase1：
      会从event-log中筛选seq，从文件末尾反向扫描，筛选按事件类型先分优先级，
      事件优先级如下（从高到底）：
         User Message、Assistant Message  ，tool-call/tool-result
         （原始 Event 中如果一个 Assistant Message 同时包含文本和多个 Tool Calls，
         可以将它拆成多个 MemoryItem，但共享同一个来源 seq ）
      读取大小限制如下：
         max_rollout_bytes	8 MiB	本次从 Session 中保留的有效历史总预算
         max_record_bytes	1 MiB	单条原始 Event 的大小上限
         tool_output_tokens	2,000	单条 Tool Result 的近似截断目标
         max_row_bytes	10,000	单条序列化记录的大小上限
      也就是读取8MB的数据并区分优先级，将其转化为统一MemoryItem，在读取时只记录原始数据，
      再根据优先级选择数据，再进行格式化并估计token，采用4字节近似法（格式化的格式参照正常输入到LLM的message格式，
      但是role变为 User Message、Assistant Message  ，tool-call/tool-result）
      同优先级按seq选择（这里工具调用和结果仍按 call_id 成组选取，
      所以较新的结果可能带入较旧的调用），最后将所有seq按顺序排列，总大小要在上下文限制内
      对上下文也有限制;
       B=w乘以input_budget_ratio`取下
        input_budget_ratio=0.7
      llm生成的结构将sqlite中的旧文件覆盖，即update

      sqlite的2张表存储在schema.sql下：
      stage1-outputs存储局部记忆，筛选时通过last-completed-seq来充当10d的限制
      通过在追加seq的循坏中记录last-completed-seq，当一轮turn结束时进行追加sqlite
      因此只有在turn中途奔溃时会不完整，此时的turn对于记忆没有帮助
      （或许可以通过记忆恢复来解决）
      每个turn之间相隔时差可能会很大，但是未完成的turn没有意义，因此代替phase1的活跃事件限制来筛选session

       memory_jobs表是phase1，2的任务控制，用来判断是否成功以及限制只有一个worker进行提取
 
文件修改方式：
  phase1：将sqlite中的旧文件覆盖，即update
  phase2：采用这个框架，通过git得出增删改，然后将哪些文件增删改，以及原本的memory在memory-agent中通过llm
  进行整合，由llm根据文件增删改的变化，判断是否要更改记忆，随后通过tool来进行改变

二、响应解析和报文
 llm返回后追加记录和工作记忆再解析，一次对话存储，user-question，llm-response，tool-message，answer
 llm的返回主流是Chat Completions 风格，这里的id和tool-call-id都是llm生成对于不同的tool
 因为一次可能调用几个相同的tool
 {
    "id": "chatcmpl-123",
    "object": "chat.completion",
    "choices": [
        {
            "index": 0,
            "finish_reason": "tool_calls",
            "message": {
                "role": "assistant",
                "content": null,
                "tool_calls": [
                    {
                        "id": "call_001",
                        "type": "function",
                        "function": {
                            "name": "get_weather",
                            "arguments": "{\"city\":\"北京\"}"
                        }
                    }
                ]
            }
        }
    ]
}

tool-call和message设计为：
@dataclass
class ToolCall:
    id: str
    name: str
    arguments: dict[str, Any]


@dataclass
class Message:（前三个与llm返回的一致，id区分不同session    metadata记录时间戳等，）
    role: str
    content: Any = None

    tool_calls: list[ToolCall] = field(
        default_factory=list
    )
    
    tool_call_id: str | None = None

    metadata: dict[str, Any] = field(
        default_factory=dict
    )
